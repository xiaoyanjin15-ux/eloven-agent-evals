# DeepSeek API 性能与费用测试说明

## 1. 这份脚本解决什么问题

`benchmark.py` 用于测试 **API 服务**：等待多久开始输出、输出多快、整个请求多久完成、多个请求同时执行时是否排队或报错，以及缓存用量和估算费用。

它不评判答案是否正确，不测 GPU 显存、模型参数量或服务器内部计算时间，不包含图片、工具调用、多轮 Agent 测试。结果包含你的网络、客户端、服务端排队、模型推理等综合影响，不能解释为纯模型计算速度。

采用 Python + OpenAI Python SDK，通过兼容的 Chat Completions 接口调用 DeepSeek。安装 openai 包不意味着调用 OpenAI 模型；实际调用哪个平台由 `base-url` 决定。

文件：

- `benchmark.py`：测试脚本。
- `requirements.txt`：运行依赖。
- `test_benchmark.py`：不联网的自动验证程序。
- `results/`：运行后生成的结果目录，已在本目录的 `.gitignore` 中忽略。

## 2. 测哪些指标

| 输出字段 | 中文含义 | 计算方法与限制 |
|---|---|---|
| `ttft_s` | 首次有效内容延迟 | 发送请求前计时，直到第一次收到非空 reasoning_content 或 content；忽略空块、角色块和保活消息。流式块可能包含多个 token，所以是客户端可观察近似 TTFT |
| `first_answer_s` | 首次正式答案延迟 | 发送到首次非空 content；包括此前的思考时间 |
| `e2e_s` | 请求总耗时 | 从调用 SDK 前到整个流读取并关闭结束；包含最后的用量消息。失败请求也记录耗时 |
| `output_tokens_per_s_est` | 总输出速度估算 | completion_tokens ÷（最后一个有效内容块时间 − 第一个有效内容块时间），包含推理与答案 token |
| `answer_tokens_per_s_est` | 正文输出速度估算 | answer_tokens ÷（最后一个正文块时间 − 第一个正文块时间） |
| `success_requests_per_s` | 成功请求吞吐量 | 阶段成功请求数 ÷ 阶段墙钟耗时 |
| `known_success_output_tokens_per_s` | 已知成功输出总吞吐量 | 成功且有用量的请求 completion_tokens 总和 ÷ 阶段墙钟耗时；不是单请求速度的平均值 |
| `failure_rate` | 失败比例 | 已尝试但失败的请求数 ÷ 已尝试请求数；尚未发出的 skipped 不计入分母 |
| `cache_hit_ratio` | 输入 token 缓存命中比例 | hit ÷ prompt；汇总时为总 hit ÷ 总 prompt，而不是对每个请求比例简单平均 |
| `estimated_cost` | 单请求估算费用 | 按你提供的三种单价与 API 返回用量计算 |

时间单位均为秒，价格单位见第 8 节。`null`、CSV 空单元格、报告里的 `—` 表示缺失或无法计算，**不是零**。

### 2.1 为什么速度字段带 est

API 返回的是内容块，不提供每个 token 的独立生成时间。首块可能已经带有多个 token。以上公式把首块 token 也放入分子，短输出时会偏高，只是近似输出速率，不能当作精确逐 token 的 TPOT/ITL。只有一个内容块时不计算速度；不是把块数当作 token 数。

脚本没有计算逐 token ITL、TPOT，也没有声称完全复现 Artificial Analysis 的测速方法。与榜单对比时，输入长度、推理档位、采样口径和网络位置必须同时考虑。

### 2.2 成功、截断与缺失用量

收到正式答案、流正常结束，并有 `finish_reason=stop` 或 `length`，记为协议层成功。

- `length` 同时记 `truncated=true`，表示输出触及上限，答案可能不完整。不会把它当成质量通过。
- 只返回推理而没有正文记 `NoAnswer`。思考模式下上限太小可能发生这种情况。
- 流结束但没有 finish_reason，记 `IncompleteStream`。
- 正常完成但缺少 usage，仍可以统计时间；token 速度、缓存与费用可能留空。
- 超时与网络中断可能发生在已经生成并计费之后。没有用量不能当成免费。

## 3. 第一次运行：逐步操作

下面命令是 **PowerShell 命令，输入终端，不是写进 Python 文件**。从本项目目录运行。

### 步骤一：打开测试目录并选择 Python

```powershell
Set-Location '.\api_benchmark'
python -c "import sys; print(sys.executable)"
```

建议使用 Python 3.11+ 的独立虚拟环境；如果系统命令不是 `python`，请替换为你本机可用的 Python 启动命令。

### 步骤二：在同一个 Python 环境安装依赖

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -c "import openai; print(openai.__version__)"
```

看到版本号说明当前虚拟环境能导入 openai。以后运行 benchmark 前，先在该目录重新执行 `.\.venv\Scripts\Activate.ps1` 即可复用同一环境。

### 步骤三：设置密钥

```powershell
$env:DEEPSEEK_API_KEY = '替换为你的完整新密钥'
```

环境变量名称是固定标签 `DEEPSEEK_API_KEY`，引号里面才是真实密钥。不要填带星号的遮挡版本，也不要把密钥写进脚本或发截图。此前公开过的密钥应撤销换新。

此写法只对当前 PowerShell 会话及其启动的程序生效。关闭终端后重新设置。请使用下面命令从同一终端运行，不要切换到另一个终端。脚本**不会自动读取项目 `.env` 文件**。

API 账户需要有余额；网页版可以聊天不代表 API 有可用余额。脚本不会替你充值。

### 步骤四：先预览，不发送请求

```powershell
& $benchPython .\benchmark.py --dry-run
```

预览会显示模型、思考模式、请求数量、并发档位和提示词字符数。dry-run 不需要密钥、不创建结果、不联网、不扣费。

### 步骤五：只发一次，确认链路正常

```powershell
& $benchPython .\benchmark.py --scenario speed --requests 1 --max-tokens 256
```

这会真实调用一次 API 并产生费用。看到 `OK` 说明收到正文并正常结束。终端会打印本次结果目录。默认禁用思考、使用 `deepseek-flash`、最多输出 256 token；达到上限会标记截断。

### 步骤六：进行 20 次初步测速

```powershell
& $benchPython .\benchmark.py --scenario speed --requests 20 --max-tokens 512
```

一次只执行一个请求，完成后发下一次。20 次适合检查流程和初步趋势，**不适合对 P95/P99 作稳定结论**。正式测试建议在预算允许时增加到每档至少 100～200 次，并在多个时段重复；这只是起点，不是统计精度保证。

## 4. 场景一：单请求与输入长度测试

speed 场景固定并发为 1。每条请求在提示词最开头加入不同的测试编号，尝试减少共享前缀缓存的影响。但不能保证绝对未命中，必须检查 `cache_hit_tokens`。

### 比较输入长度

```powershell
& $benchPython .\benchmark.py --scenario speed --requests 20 --context-chars 2000
& $benchPython .\benchmark.py --scenario speed --requests 20 --context-chars 20000
& $benchPython .\benchmark.py --scenario speed --requests 20 --context-chars 100000
```

`context-chars` 是内置资料的**字符数量，不是 token 数**。脚本还会添加问题和测试编号，所以实际 prompt_chars 更大。真实输入长度看 API 返回的 prompt_tokens；不要将上述三组写成“2K、20K、100K token 测试”。

内置资料由重复的中文服务记录构成，便于快速制造长输入，但不代表真实业务资料的分布。它适合冒烟与机械性能测试。正式测试可用自己的脱敏文本：

```powershell
& $benchPython .\benchmark.py --prompt-file .\my_prompt.txt --requests 20
```

手动创建 UTF-8 编码的 `my_prompt.txt`，里面应包含**完整任务要求和资料**。该文件替换内置提示词，context-chars 此时不生效。内容会发送给你配置的 API 服务商；脚本只将字符数和 SHA256 写入结果，不保存提示词正文。

### 比较思考模式

```powershell
& $benchPython .\benchmark.py --thinking disabled --requests 20 --max-tokens 2048
& $benchPython .\benchmark.py --thinking enabled --effort high --requests 20 --max-tokens 2048 --timeout 300
```

思考开启时发送 thinking.type=enabled 和 reasoning_effort；关闭时不发送 effort。推理输出可能占用输出预算。出现 NoAnswer 或大量 length 时，提高上限后另开一组测试，不要混合两组结果。

脚本不设置 temperature/top_p，使用服务默认值；记录了输入与输出用量以便检查输出长度差异。同样 max-tokens 只是同样上限，不保证回答长度相同。

## 5. 场景二：并发与稳定性测试

```powershell
& $benchPython .\benchmark.py --scenario load --requests 40 --concurrency 1 2 4 8 --max-tokens 512
```

执行顺序如下：

1. 并发 1，执行总共 40 次。
2. 并发 2，执行总共 40 次。
3. 并发 4，执行总共 40 次。
4. 并发 8，执行总共 40 次。

总计最多 **160 次请求**，不是 40 次，也不是每个并发用户各发 40 次。参数 requests 默认只有 5，正式负载测试应显式指定更多请求，否则并发 8 也最多只有 5 个在途请求。

采用固定并发的**闭环负载**：一个请求结束，worker 立刻领取下一条。并发 8 表示最多 8 个在途请求，不代表每秒发送 8 次。开始和收尾阶段并发较低；报告总吞吐量包含这些阶段。

脚本没有固定请求到达率、持续时间模式或最大容量搜索，因此不能据此宣称测出服务商极限 QPS。每档按指定次序执行，存在时段影响；正式比较可反转顺序或分时复测。

重点观察：并发提高后总吞吐量是否增加、TTFT/正文延迟 P95 是否明显变大、是否出现 429、超时或 5xx。不要只看成功请求延迟而忽略失败率。

整个测试共用一个异步 HTTP 客户端，允许连接复用；没有专门的连接预热阶段，因此各阶段的连接状态未必完全相同。默认最多 8 并发适合初步测试；更高并发时还应排查客户端连接池、带宽与账户限额。

## 6. 场景三：缓存对比

```powershell
& $benchPython .\benchmark.py --scenario cache --requests 20 --context-chars 20000 --cache-wait 5
```

总计最多 **41 次请求**：

| 阶段 | 请求数 | 做什么 |
|---|---:|---|
| unique_prefix | 20 | 每次在提示词开头加入不同编号，尝试减少缓存命中 |
| repeated_prefix 的 primer | 1 | 发出待复用的完整提示词，为缓存建立创造条件 |
| 等待 | 0 | 等待 5 秒，允许缓存持久化；不能保证已经生效 |
| repeated_prefix 的 measure | 20 | 串行重复完全相同的提示词，观察实际命中 |

primer 写入逐请求结果，也计入全局已知费用，但不计入重复组的速度、吞吐量和测量费用汇总；等待时间也不计入该组墙钟时间。

重复输入不保证命中。脚本优先读取 prompt_cache_hit_tokens / prompt_cache_miss_tokens，兼容 prompt_tokens_details.cached_tokens；只有输入总数和命中/未命中数能相互核对，才计算缓存比例与费用。

因此报告使用 unique/repeated，而不是声称已经完成严格“冷缓存/热缓存”实验。只有检查真实 hit/miss 后，才能作这种解释。缓存命中复用输入计算，模型仍然会重新生成答案。

## 7. 比较 Flash、Pro 或不同服务商

```powershell
& $benchPython .\benchmark.py --model deepseek-flash --requests 20 --thinking enabled --effort high --max-tokens 2048
& $benchPython .\benchmark.py --model deepseek-v4-pro --requests 20 --thinking enabled --effort high --max-tokens 2048
```

截至 2026-09-24，官方文档将 deepseek-flash 对应到 V4.1 Flash；旧的 deepseek-v4-flash 名称也可能被路由到新版。运行前查官方说明，不能把旧别名当成旧权重。脚本同时保存 requested_model、response_model 和 system_fingerprint（若提供），但返回的模型名也可能只是别名，**不保证确切权重身份**。

比较第三方服务商可修改 base-url、model、api-key-env，并提供该服务商的密钥与价格。例如：

```powershell
$env:PROVIDER_API_KEY = '该服务商的密钥'
& $benchPython .\benchmark.py --base-url 'https://你的服务商地址/v1' --api-key-env PROVIDER_API_KEY --model '服务商实际模型ID' --requests 1
```

这是参数示意，先替换占位符。第三方即使兼容 Chat Completions，也未必支持 DeepSeek 的 thinking 参数和 usage 扩展字段；400 时应先确认兼容性，而不是反复重试。不同服务商密钥不能混用。

## 8. 如何计算费用

默认不填价格，费用字段为空。脚本不会自动查询价格，也不硬编码会变化的价格。到所用服务商核对币种、峰谷时段、缓存价格和输出价格后，填写三项：

```powershell
& $benchPython .\benchmark.py --requests 5 --input-price 1 --cache-price 0.1 --output-price 2 --currency USD
```

**上面 1、0.1、2 是演示单价，不是 DeepSeek 当前报价，正式测试必须替换。**三项都是每百万 token 的价格，且必须使用同一币种。

```text
费用 = (未命中输入 token × input-price
      + 命中输入 token × cache-price
      + completion_tokens × output-price) / 1,000,000
```

举例：未命中输入 1,000、命中输入 9,000、输出 500，按演示价格计算：

```text
(1000 × 1 + 9000 × 0.1 + 500 × 2) / 1,000,000 = 0.0029 USD
```

completion_tokens 包含推理输出时，不再把 reasoning_tokens 加一次，避免重复计费。正文 token 用 completion_tokens 减 reasoning_tokens 得到；思考模式下接口不提供拆分时，正文 token 和正文速度留空。

估算未包含第三方额外缓存写入/存储费用、优惠、税费、最低收费、工具费等。一轮中单价视为固定，不自动切换峰谷；跨时段应分开跑。没有 usage 的失败请求可能已收费，因此 known_total_cost 仅代表已知部分，最终以平台账单为准。

脚本不提供硬性金额预算截止，只通过请求数、max-tokens 和超时限制规模。先 dry-run 看总请求数，再少量试跑，结合实际 prompt_tokens/输出用量估计正式测试预算。

## 9. 结果文件怎么看

每次运行都会新建独立目录，例如 `results/20260924_153000_a1b2c3d4e5f6/`：

| 文件 | 用途 |
|---|---|
| config.json | 参数、Python 路径、系统、SDK 版本、运行 ID；不保存 API Key |
| requests.jsonl | 每完成一个请求立即追加并刷新，保留原始 usage；不保存提示词和回答正文 |
| requests.csv | 一行一个请求；UTF-8 BOM 便于 Excel 打开中文；含 primer |
| summary.json | 各阶段统计、P50/P95/P99、吞吐量、失败率、缓存比例、费用覆盖情况 |
| report.md | 便于阅读的简要结果表，精确费用和完整数据看 JSON/CSV |

### 建议阅读顺序

1. 看失败率和 errors：大量失败时不要先比较速度。
2. 看 truncated_count：大量截断说明输出预算可能影响结论。
3. 看 prompt_tokens、completion_tokens 的分布：确认对比组工作量接近。
4. 看 TTFT、first_answer、e2e 的 P50/P95。
5. 看总吞吐量和 successful_token_usage_coverage：低覆盖时吞吐量只含已知用量，不是完整总数。
6. 看 cache_usage_rows、cache_hit_ratio 与 cost_known_rows：确认缓存和费用是否足够完整。

P50 是中位数，P95 是估计 95% 样本不超过的值。实现使用排序后线性插值。延迟与单请求速度汇总只包含成功请求；失败请求的耗时仍保存在 CSV，失败率另列。不同指标有效样本数可能不同，metrics 中的 n 表示真实分母。

`known_estimated_cost` 是一个阶段 measure 请求可计算费用之和；`known_total_cost` 包含所有已记录请求及 primer。不要将空值填 0 后汇总。

## 10. 出错怎么办

| 现象 | 处理 |
|---|---|
| No module named openai | 用 `$benchPython -m pip install -r requirements.txt` 安装到运行脚本的同一环境 |
| 环境变量未设置 | 在同一 PowerShell 中设置 DEEPSEEK_API_KEY，再运行；脚本不读取 .env |
| 400 | 参数、模型或服务商接口不兼容；查配置 |
| 401 | 密钥无效、过期或用错平台 |
| 402 | 账户余额不足；充值到账后再跑 |
| 403 / 404 | 权限、模型 ID 或 base-url 有问题 |
| 429 | 限流；先降低并发并核对账户额度 |
| 5xx | 服务端错误；保留结果，在另一时段重新测试 |
| RequestDeadlineExceeded | 请求超过 timeout 总时限；先检查网络、思考预算，再决定是否提高 timeout |
| NoAnswer | 未收到正文，可能思考耗尽输出预算；提高 max-tokens 另测 |
| IncompleteStream | 流未正常结束；可能网络中断或服务返回不完整 |

自动重试固定为 0，避免重试把失败率和耗时掩盖。收到 400/401/402/403/404 时停止启动新请求和后续阶段，但已在途请求仍会完成并记录；429/5xx 则继续剩余有限数量请求，以观察错误比例。

错误日志只存错误类型与 HTTP 状态，不保存服务端错误正文，防止正文意外回显密钥/私有输入。必要时在平台控制台排查。

按 Ctrl+C 中断时，已完成请求会保留，当前未完成阶段可能没有汇总；在途请求不保证完整入账。强制结束进程或断电可能只有 JSONL，未必来得及生成 CSV/报告。

## 11. 公平比较与测试范围

- 固定相同客户端、网络、资料、任务要求和推理设置，再改变单一变量。
- max-tokens 是输出上限，不是强制输出长度。不同长度会影响总耗时。
- 请求编号与内置重复资料会影响工作负载，正式业务测试应使用代表性脱敏样本。
- 思考档位名称相同不保证跨模型计算预算相同，解释结果时保留这点。
- 全部请求是独立单轮对话；无工具、图片和聊天历史。
- 缓存模式串行比较，不能直接代表并发冷启动下的命中情况。
- 不要把本脚本的总吞吐量当作服务商全局容量，它只是你的账户在该负载下的观测。
- 不要只凭一次运行宣布某模型更快；至少在不同时间复测，并报告样本数与失败率。
